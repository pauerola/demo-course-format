Training on one GPU

Section 4 of 7

Can a computer learn to spot a fracture?

1 exercise

In short
  • Transfer learning starts with a model trained on everyday photos and fine-tunes it on our X-rays.
  • device=0 trains on a single GPU, and the GPU dashboard shows it working.
  • Always compare accuracy with a simple baseline.
  • With imbalanced data, look at the recall (sensitivity) for the class you care about most.

4.1 The model

We’ll use YOLOv8n-cls, a small image classification model from the Ultralytics library. It’s a convolutional neural network, a type of neural network that picks out patterns such as edges, textures and shapes in different parts of an image.

To train a model like this from scratch, we’d need far more than 4,000 images. Instead we use transfer learning. We start with a model that has already been trained on more than a million everyday photos (the ImageNet dataset), so it has already learned to recognise general visual patterns, and then we fine-tune it on our X-rays.

4.2 Training settings

hpc-for-ai.ipynb
EPOCHS = 50
IMG_SIZE = 512
BATCH = 64
WORKERS = 8
Setting What it means
EPOCHS The number of times the model sees every training image.
IMG_SIZE The width and height, in pixels, of the square each image is turned into.
BATCH The number of images the model looks at before it updates its weights.
WORKERS The number of CPU processes loading images in the background, so the GPU doesn’t have to wait for them.

4.3 Train

Open the GPU dashboard before you run the next cell so that you can watch the GPU while the model trains.

hpc-for-ai.ipynb
model = YOLO(WEIGHTS)

start = time.perf_counter()
model.train(
    data=str(SPLIT_DIR),
    epochs=EPOCHS,
    imgsz=IMG_SIZE,
    batch=BATCH,
    workers=WORKERS,
    device=0,  # one GPU
    project=str(RUNS_DIR),
    name="1gpu",
    exist_ok=True,
    seed=42,
)
time_1gpu = time.perf_counter() - start
print(f"Training on 1 GPU took {time_1gpu / 60:.1f} minutes")

device=0 tells Ultralytics to use GPU 0 only. project and name tell it where to save the results, which in this case is runs/1gpu in your scratch folder.

While it’s training, Ultralytics prints a line for each epoch with the loss, which measures how wrong the model is on the training images, and the accuracy on the validation set. The loss should go down and the accuracy should go up.

4.4 How did training go?

Ultralytics saves some plots of the training run in the run’s folder. This cell shows the main one.

hpc-for-ai.ipynb
run_1gpu = RUNS_DIR / "1gpu"
display(ShowImage(filename=str(run_1gpu / "results.png"), width=800))

Compare the two loss plots. If the training loss keeps falling but the validation loss starts to rise, the model is overfitting: it’s learning details of the training images that don’t help with new ones. You may see this towards the end of our run. This is one reason Ultralytics saves the epoch that did best on the validation set as best.pt, as well as the final one.

Going deeper: the training plots

Each small plot shows one measurement, with the epoch number along the bottom. The blue line is the value at each epoch, and the dotted orange line is a smoothed version that makes the trend easier to see.

Plot What it shows What you want to see
train/loss How wrong the model is on the training images Going down
val/loss How wrong the model is on the validation images, which it doesn’t learn from Going down, then levelling off
metrics/accuracy_top1 The proportion of validation images the model classifies correctly Going up, then levelling off
metrics/accuracy_top5 Whether the right answer is in the model’s top five guesses Ignore it: with only two classes, it’s always 1

4.5 Test the model

The version of the model that did best on the validation set is saved as best.pt. We load it, ask it to classify every image in the test set, and compare its answers with the real labels. * in the path means “anything”, so test/*/*.jpg matches every image in both class folders. The folder each image is in tells us its real label.

hpc-for-ai.ipynb
def evaluate(weights):
    """Classify every test image and return the true and predicted labels."""
    model = YOLO(weights)
    true, pred = [], []
    test_images = str(SPLIT_DIR / "test" / "*" / "*.jpg")  # every image in every class folder
    for result in model.predict(test_images, imgsz=IMG_SIZE, stream=True, verbose=False):
        true.append(Path(result.path).parent.name)  # the folder name is the true label
        pred.append(result.names[result.probs.top1])  # the class the model thinks is most likely
    return true, pred

true, pred = evaluate(run_1gpu / "weights" / "best.pt")
print(classification_report(true, pred, digits=3))

ConfusionMatrixDisplay.from_predictions(true, pred, cmap="Purples")
plt.title("1 GPU: test set")
plt.show()

classification_report gives three scores for each class:

Score What it tells us about the fractured class
Precision When the model says “fractured”, how often is it right?
Recall What proportion of the real fractures did the model find? This is also called sensitivity.
F1-score A single score that combines precision and recall.
Support How many images of that class are in the test set.
Going deeper: the summary rows and the confusion matrix

The rows at the bottom of the report summarise both classes:

Row What it means
accuracy The proportion of all test images the model classified correctly.
macro avg The plain average of the two classes’ scores, so each class counts equally.
weighted avg The average weighted by support. There are many more not_fractured images, so this is close to the not_fractured scores.

Below the report is a confusion matrix, which compares the model’s answers with the real labels. The real label is up the side and the model’s answer is along the bottom, and each box shows a number of images. The correct answers are on the diagonal, from top left to bottom right. The missed fractures are in the fractured row, not_fractured column, and the false alarms are in the not_fractured row, fractured column.

4.6 Is that accuracy any good?

hpc-for-ai.ipynb
baseline = (test_df["fractured"] == 0).mean()
print(f"Always guessing 'not fractured' would be {baseline:.1%} accurate")

Most of the images don’t show a fracture, so a “model” that always said “not fractured” would be right over 80% of the time, and it wouldn’t find a single fracture. That’s why accuracy on its own can be misleading when the data is imbalanced.

If we wanted to use this model to decide which scans to look at first, the most important score would be the recall for the fractured class. Missing a fracture is worse than a false alarm that a clinician can check and rule out.
